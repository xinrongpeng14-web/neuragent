## 4. 发现的缺陷：键的符号位翻转

### 4.1 现象

脱离 PG、直接调用 SELIX 库的独立程序 `selix_repro.cpp` 复现了同样的问题：

| 情形 | bulk_load 后点查 | 持续插入 |
|---|---|---|
| 翻转符号位（原版行为） | 20 万键中 **1024 个找不到** | 插入 700 到 800 条之间进程被系统杀掉 |
| 不翻转（原始键） | 20 万键全部找到 | 10 万条全部成功，内存稳定在 14MB，随后 30 万次点查 0 错误 |

### 4.2 根因

`indexengine.cpp:27-29` 的 `encode_key_64` 把键与 `0x8000000000000000` 异或。小的正整数键因此被映射到 −2^63 附近。SELIX 的线性模型用 double 计算位置，而 double 在这个量级上的最小间隔是 1024。键值相差不到 1024 的键在模型中完全相同，于是：

- bulk_load 划分节点时用模型反推边界，边界附近的键被分到错误的节点，之后查不到。
- 插入时模型对一大片键给出相同的预测位置，节点反复扩容也无法把键分开，内存无限增长。

这个翻转本身没有必要：`lit::Lit<int64_t, ...>` 直接按有符号整数比较，顺序本来就是对的。

### 4.3 修复

补丁 `0001-selix-no-sign-flip.patch` 把 `encode_key_64` 与 `decode_key_64` 改为恒等变换，共改动一个文件。已确认可以干净地应用到仓库：

```bash
cd /home/zhanhao/neuragent/NeuralDB
git apply /home/zhanhao/neuragent/prototype/p1/0001-selix-no-sign-flip.patch
```

补丁**尚未应用到仓库**，只在容器内的编译副本上生效。

### 4.4 修复后的残余限制

键的绝对值超过 2^53 时 double 仍然无法精确表示，同样的问题会再次出现。YCSB 的整数键远小于这个范围，雏形实验不受影响。

## 5. 使用 nrindex 时必须遵守的约束

### 5.1 规划器默认不选 nrindex

nrindex 的代价估计函数把选择率固定为 1.0。对 20 万行的表，规划器估出的索引扫描代价是 9482，高于顺序扫描的 4370，因此默认走顺序扫描。

YCSB 连接需要执行：

```sql
SET enable_seqscan = off;
SET enable_bitmapscan = off;   -- 可选；位图扫描经 nrindex 也能得到正确结果
```

### 5.2 常量类型必须是 bigint

nrindex 的操作符类只注册了 `int8 = int8`。`WHERE k = 123456` 中的常量是 int4，匹配不到索引。必须写成 `WHERE k = 123456::int8`，或使用 bigint 类型的绑定参数。

### 5.3 非等值查询会静默返回错误结果

| 查询 | 经 nrindex | 经顺序扫描 |
|---|---|---|
| `WHERE k BETWEEN 1000 AND 1100` | 0 行 | 101 行 |
| `SELECT count(*) FROM ycsb`（seqscan 已关闭） | 0 | 30 万 |

关闭顺序扫描后，连不带条件的全表查询也会走 nrindex 并返回空结果，且没有任何报错。**YCSB 连接上只能执行等值点查与插入**；行数统计等其他查询必须在另一个未关闭顺序扫描的连接上做。

### 5.4 索引只存在于建索引的连接里

其他连接查询时规划器照样选择 nrindex，但该连接内的 SELIX 实例是空的，结果是静默返回 0 行。在新连接内执行 `REINDEX INDEX ycsb_k_nr` 会在该连接内重建索引。雏形方案中"YCSB 专用连接在回合开始时自己建索引"的做法因此成立。

注意：`REINDEX` 只在**全新的连接**里验证过。回合重置时仍应先删索引、再装载数据、最后由新连接建索引。如果装载数据时索引还在，执行装载的连接会把每次插入写进它自己的私有 SELIX 实例，造成内存累积。

### 5.5 C++ 部分未开优化

nr_am 的 Makefile 编译 `indexengine.cpp` 时只有 `-std=c++17 -march=native`，没有 `-O2`。SELIX 是纯头文件模板库，未优化时性能明显偏低。雏形实验前应在 `PG_CXXFLAGS` 中加入 `-O2`。本报告第 6.1 节的 SQL 层数据是在未优化的编译下测得的。

## 6. V4 实测数据

以下数据在 2 核主机、容器限 1.5 核的条件下测得，同机还有其他容器在运行。两次重复运行之间的波动可达 2 倍，数值只用于判断量级。

### 6.1 SQL 层：单连接服务端吞吐

表有 100 万行。用 PL/pgSQL 循环执行 20 万次操作，不含客户端往返；每次操作都重新规划。

| 操作 | nrindex | btree |
|---|---|---|
| 点查 | 9,149 次/秒，约 109 微秒/次 | 6,674 次/秒 |
| 随机键插入 | 14,827 次/秒，约 67 微秒/次 | 15,404 次/秒 |
| 插入后点查 | 8,396 次/秒 | 7,214 次/秒 |

建索引耗时：nrindex 1.24 秒，btree 1.85 秒。建 nrindex 后后端进程内存增加约 42MB；同样数据的 btree 索引为 21MB。

### 6.2 索引层：SELIX 三档参数的差异

脱离 PG 直接调用 SELIX，以 `-O2` 编译。先 bulk_load 100 万键，再执行 100 万次混合操作。三档参数取自 `GlobalAgent_prototype.md` 5.3 节。两次运行的结果都列出。

| 档位 | 读 90% 单次耗时 | 读 30% 单次耗时 | 初始内存 | 读 30% 后内存 |
|---|---|---|---|---|
| compact（8MB，0.80/0.90/0.70） | 0.15 – 0.26 微秒 | 0.42 – 0.77 微秒 | 19.2MB | 34.7MB |
| default（16MB，0.70/0.80/0.60） | 0.20 – 0.49 微秒 | 0.36 – 0.71 微秒 | 22.0MB | 41.2MB |
| loose（32MB，0.50/0.60/0.40） | 0.25 – 1.48 微秒 | 0.57 – 1.82 微秒 | 30.8MB | 54.3MB |

两次运行中 loose 档都是最慢的，这与雏形方案中"loose 档费内存但插入快"的假设相反。

## 7. 对雏形方案的影响

### 7.1 SELIX 动作在 SQL 层面很可能观测不到

| 量 | 数值 |
|---|---|
| SQL 层单次操作耗时 | 约 67 到 109 微秒 |
| SELIX 单次操作耗时 | 约 0.15 到 1.8 微秒 |
| SELIX 占比 | 约 0.2% 到 3% |
| 三档参数之间的最大差值 | 约 1.2 微秒，相当于 SQL 层单次耗时的 1% 到 2% |

雏形方案的判定门槛是综合回报提升 5%，标定时要求的噪声上限是 10%。SELIX 档位切换对 YCSB 吞吐的直接影响预计低于 2%，落在噪声之内。

**这个估计的局限**：6.1 节的 SQL 层耗时包含每次重新规划的开销，且 C++ 部分未开优化。真实客户端使用预备语句时单次耗时会更低，SELIX 的占比会相应升高，但加上客户端往返后预计仍在 10% 以下。实际占比需要在 P2 到 P9 完成后用真实的 YCSB 驱动测量。

### 7.2 内存耦合需要大得多的索引

三档参数的内存差异约为每 100 万键 10 到 20MB。要让这个差异影响页缓存，差值需要达到数百 MB 以上，对应至少数千万个键。

### 7.3 当前主机无法承载雏形实验

| 雏形方案要求 | 当前主机 |
|---|---|
| 容器绑定 4 个 CPU 核，实验程序另占若干核 | 共 2 核 |
| IMDB 数据集加 YCSB 表，内存上限要让数据放不进页缓存 | 共 3GB 内存 |
| neurqo_frame 多进程，每个进程加载 PyTorch 模型 | 内存不足 |

P1 这种单连接功能验证可以在本机完成，第 7.1 节的原版运行、训练与评估需要更大的机器。

### 7.4 可选的应对方向

这三个方向互不排斥，由你决定：

1. **保留 SELIX，放大其影响。** 把索引规模提高到数千万键，让内存差异达到可观测的量级；同时用预备语句降低 SQL 层开销。需要更大的机器。
2. **保留 SELIX，改变观测指标。** YCSB 的回报不用 SQL 层吞吐，改用 SELIX 内部的单次操作耗时或结构调整次数。这样 GA 的 SELIX 动作有明确的效果，但它与 NQO 之间的耦合只剩 CPU 一条。
3. **第一版换一个子 agent 或动作组。** 例如用 `work_mem` 作为第二个动作组，它对 JOB 查询的影响是直接的。这对应 `GlobalAgent_prototype.md` 第 9 节风险表中的备选方案。

## 10. 补充测量（选定方向 2 之后）

选定"SELIX 一侧改用索引层指标"之后，为重新确定 SELIX 档位补做了三组索引层测量。全部脱离 PG，以 `-O2` 编译，取 3 次运行的中位数。原始输出在 `results/selix_sweep.txt`、`selix_online.txt`、`selix_dist.txt`。

### 10.1 节点大小与密度的静态扫描

先按指定参数装载 100 万键，再执行 100 万次操作。每格为"单次耗时（微秒）/ 操作后内存（MB）/ 结构调整次数"。

| 节点 | 密度 init/max/min | 读 90% | 读 30% |
|---|---|---|---|
| 4MB | 0.85/0.95/0.75 | 0.16 / 19.4 / 148 | 0.39 / 33.3 / 156 |
| 4MB | 0.70/0.80/0.60 | 0.20 / 23.6 / 42 | 0.35 / 41.2 / 51 |
| 4MB | 0.50/0.60/0.40 | 0.13 / 32.9 / 66 | 0.32 / 46.7 / 82 |
| 4MB | 0.30/0.40/0.20 | 0.22 / 55.7 / 99 | 0.33 / 81.5 / 152 |
| 16MB | 0.85/0.95/0.75 | 0.17 / 19.4 / 148 | 0.31 / 33.3 / 156 |
| 16MB | 0.70/0.80/0.60 | 0.11 / 23.6 / 42 | 0.32 / 41.2 / 51 |
| 16MB | 0.50/0.60/0.40 | 0.14 / 32.9 / 66 | 0.27 / 46.7 / 37 |
| 16MB | 0.30/0.40/0.20 | 0.16 / 55.7 / 99 | 0.37 / 81.5 / 152 |
| 64MB | 0.85/0.95/0.75 | 0.21 / 22.0 / 215 | 0.36 / 30.4 / 350 |

### 10.2 运行中切换档位

以默认参数装载 100 万键，运行中切换档位，统计切换后 120 万次操作。每格为"单次耗时（微秒）/ 末尾内存（MB）/ 切换后结构调整次数"。

| 键分布 | 读比例 | dense | default | sparse |
|---|---|---|---|---|
| 均匀 | 90% | 0.16 / 23.4 / 0 | 0.30 / 29.3 / 0 | 0.23 / 43.9 / 2 |
| 均匀 | 30% | 0.33 / 39.6 / 6 | 0.26 / 52.1 / 4 | 0.34 / 87.9 / 8 |
| 对数正态 | 90% | 0.17 / 28.0 / 9 | 0.32 / 33.7 / 9 | 0.64 / 48.0 / 9 |
| 对数正态 | 30% | 1.28 / 50.0 / 973 | 1.02 / 56.8 / 69 | 0.99 / 91.0 / 64 |

逐段数据（`results/selix_online.txt`）显示，切换后的效果在 20 万到 40 万次操作内就能观察到。

### 10.3 三点结论

1. **内存与结构调整次数是确定性的。** 内存随密度单调变化，dense 到 sparse 相差约 2 倍。
2. **最优档位随负载变化。** 读多时 dense 更快也更省内存；写多时 default 或 sparse 更快，dense 的结构调整激增。
3. **耗时的噪声与档位差异在同一量级。** 本机两次运行可相差 2 倍。10.2 节用的是随机键；另一组按顺序生成键的测试中，读多时切到 dense 反而慢了 2 到 3 倍。耗时方向需要在更安静的机器上、用真实的 YCSB 驱动确认。
